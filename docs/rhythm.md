# 节奏识别系统（RhythmKit）

把「音乐」App 的声音变成灯光能用的节奏事件。整体参照实时节拍跟踪的成熟做法：
起音检测函数（onset detection function）→ 自相关 + 梳状模板测速度 → 累计得分（Ellis 2007 /
BTrack 一类）跟踪拍点 → 显式状态机决定是否输出节拍。渲染层只消费事件，不做任何判断。

```
音频（「音乐」进程，~10ms 一块）
  │
  │  三个时间尺度（TimeScale，2026-10-28 统一）：分析里每个参照都只看其中一个——
  │    此刻 1 s（找打击的门槛、各频段在混音里的分量、低频持续部分）、
  │    段落 8 s（重击排名、低频冒出部分、flux 的常态）、整首 60 s（打击大小、各频段响度、活跃度的常态）
  │
  ▼ ① FeatureExtractor（音频线程，帧率 ≈ 94 Hz）
  │    FFT 1024 / hop 512，Hann 窗；对数压缩 Y=log(1+γ|X|)
  │    三个频段的谱通量 F_b = Σ max(0, Y_t − Y_{t−1})：低 30–150 Hz、中 150–6000 Hz、高 6000–16000 Hz（首尾相接）
  │    每个频段用自己的段落均值归一化（AdaptiveScale，τ = 8 s，启动阶段做偏差校正）→ flux，用来"找打击"
  │    另算线性幅度上的谱通量 rawFlux（不压缩、不归一化），随真实音量变化，用来"定大小"
  │    （对数通量与音量无关——音量降到 30% 它几乎不变，所以不能拿来判断一下有多响）
  │    起音函数 O = 1.0·低 + 0.8·中 + 0.5·高；各频段响度（AdaptiveScale 峰值，半衰期 60 s）；
  │    各频段原始能量（三个频段之间可比，用来算各自在混音里的分量）
  │
  ▼ ② RhythmAnalyzer（同一线程，逐帧）
  │    ├ PeakPicker：每个频段找"打击"——局部极大（±3 帧）、高于此刻（1 s）均值 + 1.5σ、
  │    │    且至少是该频段常态的 2 倍；同频段至少间隔 80 ms（高频 50 ms：密集的踩镲、沙锤每秒到 20 下也一下下认出来）；
  │    │    确认需看后 3 帧（约 32 ms 延迟）；一下的大小 = 峰值帧和前后各一帧的 rawFlux 之和（不受分帧对齐影响）
  │    ├ 打击是不是本频段真实的一部分（BandShares）：任何频段占混音不到 −50 dB（1e-5）时它的打击都不算——
  │    │    风铃漏进低、中频的残响只占 1e-6 以下，六首歌里最安静的真实频段也在 1e-4 以上；
  │    │    低频另须"低频是混音里实在的一部分"（下面的 present > 0，即占比 ≥ 10%）：低频驱动的一切——打击、重底鼓、收紧——同一个前提；
  │    │    中频另须起音 ≥ 本频段能量水平的 0.2（每个频点的起音 ÷ √(能量 ÷ 频点数)）：和弦上的风铃残响约 0.08、
  │    │    和弦自身的拍频起伏约 0.1，六首歌的真实中频打击第 10 百分位在 0.3 以上。这个量偏向压低单音（能量集中在
  │    │    几个频点），在中频正好分开残响和打击，用到高频则会把风铃这样的单音打击低估到十分之一，所以只用在中频
  │    ├ TempoEstimator：每 0.5 s 对最近 6 s 的 O 做自相关 A(τ)；
  │    │    梳状得分 S(τ)=Σ_{m=1..4} A(mτ)/m，乘以速度先验 P(τ)=exp(−½(log₂(τ/0.5s)/0.9)²)
  │    │    → 速度 τ*、周期性置信度 c = 标准（有偏）自相关 r(τ*) = Σx_t·x_{t−τ}/Σx_t²
  │    ├ BeatTracker：累计得分 C(t)=(1−α)O(t)+α·max_v W(t−v)C(v)，W 为以 τ* 为中心的对数高斯，α=0.9
  │    │    每拍过半时向前推演 C，预测下一拍时间 T（提前给出，渲染可以让峰值正好落在 T）
  │    ├ 一下有多大：rawFlux ÷ 本频段整首（60 s）打击的第 90 百分位（BandReference）——底鼓和底鼓比、军鼓和军鼓比
  │    ├ 是不是重击（Ranking，重底鼓、中频重击、重音共用一套）：在段落（8 s）里同频段的其他打击中排名，
  │    │    相差 10% 以内算并列（各算一半在上、一半在下），排进前 25% 即是（重音 SalienceDetector 用 30%）；
  │    │    每半拍最多一个（速度未知时 0.25 s），间隔内只放行更大的一下，弱的不会挡住强的
  │    ├ SalienceDetector（重音，只供 rhythm-eval 离线对照）：40 ms 内的低频+中频打击合为一击，
  │    │    大小 = 1.0·低 + 0.8·中（底鼓是人感到的重拍），按上面同一个排名
  │    └ 状态机（带回滞）：
  │         平缓    —— 节奏活跃度 a < 0.3 持续 1.5 s：不出拍、不出闪烁，只剩颜色缓慢变换
  │         寻拍    —— a ≥ 0.45 但置信度不足：只有重击，没有网格拍
  │         锁定    —— 置信度 ≥ 0.25 连续两次：重击 + 预测的网格拍；置信度 < 0.12 持续 3 s 退回寻拍
  │         活跃度 a = 最近 2 s 低/中频打击强度之和 ÷ 整首（60 s）内这个和的第 75 百分位
  │         （没有打击的平缓段自然为 0；用起音函数均值不行——它已按长期均值归一化，恒在常数附近）
  │         强度 intensity = smoothstep((a−0.3)/0.4)，1 s 平滑——整体律动的强弱；
  │         各频段自己的效果按自己的大小：中频提亮按中频打击大小 × intensity，高频闪点只按高频打击大小
  │
  ▼ 事件（带时间戳，跨线程队列）
       三个频段各管各的（2026-10-27 去掉底鼓 / 军鼓联动识别）：低频的打击就是底鼓候选，中频、高频的打击各自提亮
       .kick(time, strength)：低频重击（底鼓或贝斯换音），strength 再乘低频的 present
       .lift(time, band: mid/high, strength, heavy)：中频或高频的打击；heavy = 中频重击
       .accent、.expectedBeat、.hit：重音、网格拍和全部打击，只供 rhythm-eval 对照，灯光不用
       快照：state、tempo、intensity、各频段响度，以及 lowDraw——
              低频（底鼓 + 贝斯）的"抽电"程度 0…1（LowDraw），取两部分中大的：
              持续——此刻（1 s）低频响度的中位数（底鼓尖峰抬不动它，只看底下垫着的贝斯），对比整首歌的低频响度，
              0.15 → 0.4 平滑升到 0.7：贝斯一直弹，光团就一直聚着，没有贝斯的段落松开；
              冒出——低频能量在段落（8 s）里的位置，第 20 百分位为 0、第 95 百分位为 1，跨度至少是顶部的 35%：
              底鼓、换音的贝斯在持续聚拢之上再收到 1；
              两部分都乘 present：此刻低频能量占三个频段的比例，10% → 30% 平滑升到 1（和弦漏进低频约 3%，
              六首歌里有贝斯、底鼓时 10–60%）

  ▼ ③ MusicGlow（渲染，60 fps）——亮度、颜色、速度的分配统一在 GlowBudget（2026-10-27 参照 HomePod Sound Glow 重做）
       单位：所有亮度都是"感知亮度" 0…1，只在最后由 DockCore.LEDOutput 换算成 LED 驱动值（伽马 2.2）、暗部防抖；
              闪光一律用"滤色" screen(a,b) = 1 − (1−a)(1−b) 叠加：永远不超过 1，新的一下一定看得见
       画布（2026-10-27 参照 HomePod 的二维光团重做）：底座是正方形，从上往下看当作一块画布，每颗灯显示它所在位置的画布颜色。
              灯的位置（M18Layout.position）：按实测的四个角分段，每条边上的灯在两个角之间均匀排开（`dock-probe ledcorners` 校准两次，
              2026-10-27：四角在 2.5 / 8.5 / 13.5 / 19.5，整数是正对某颗灯、.5 是两颗之间）——前后边各 6 颗、左右边各 5 颗，
              从左边往下逆时针：0 在左边正中、前边中点在 5/6 之间、11 在右边正中、后边中点在 16/17 之间；
              之前假设的"每边均匀 5.5 颗"让前边中点偏左半颗、后边中点偏右半颗；
              短灯条 22、23 是圆键两侧的横条（中心在宽度 0.21 / 0.79、离前边 0.17，长 0.12；先按实物照片定，
              再在律动可视化里对着灯带左右对称地拖到位后固定下来，2026-10-27），取色沿灯条长度平均；
              底座实测约 1.1 宽 : 1 深，按正方形处理
       分工（2026-10-27 参照 Sound Glow 的二维图案重做）：只有低频动光团——把主题色"收"向边缘、压暗、加浓；
              中频是"放"——在边上提亮、扩散，不碰光团；高音只在鼓停下时闪点。两者叠出区分度：
              低频（底鼓、贝斯）在响时，中频提亮点亮颜色本身的色相、完全饱和，不闪白；没有低频时，重的提亮闪白
       画布三层：底是白色（封面里的白，没有就是带主题色调的白；还没取到颜色时就是纯白）；
              封面的其他颜色（最多 3 种）各是一个软边光团，在白底上漂（半径 √(0.7·占比/π)，至少 0.4）；

              收的起势和中频提亮一样稍缓，0.08 s 实看偏猛，2026-10-27），

              白底和其他颜色露出来；整体压暗 50%（30% 实看不明显；80% 太暗，暗处小的颜色通道被量化掉，混色变成极饱和的纯色，2026-10-27），颜色加浓——朝这个颜色在灯珠上最鲜艳的样子靠（同色相、去掉白的成分），

       统一换位规则（MusicGlow.place）：中音提亮、高音闪点都在边上随机的新位置（固定种子，同样的音乐出同样的灯），

              其余只是"润"一下：亮度 0.3·强度·intensity，范围 0.12 圈，颜色朝最鲜艳的样子靠、从不发白（测试 lightMidHitsOnlyGlow）；

              闪点正该出现却淡掉了，2026-10-28）；两次至少隔 0.04 s，高频多密闪点就多密，不落在还亮着的闪点 0.12 圈以内

       一种色相要占封面 5% 以上才入选，最多 4 种，取这些像素的平均色原样使用：
       不提彩度、不挪明度、不补封面没有的相邻色相；

       （2026-10-25 改：旧规则先按 HSV 挑色再强制提彩度，灰白封面会被染成饱和蓝）
```

## 设计约束

- **唯一的打击来源**：所有"这里有一下"的判断都来自 PeakPicker，渲染层不再自己看电平跳变。
- **唯一的自适应机制**：所有归一化都用 `AdaptiveScale`，时间常数写在一个地方。
- **分析与渲染解耦**：分析跑在音频帧率上，事件带时间戳；渲染帧率不影响识别精度。
- **可回放**：特征帧（不是音频）可以录成文本，`dock-probe rhythm-replay` 离线重跑 ②，
  不保存任何可还原音乐的数据。录制：在通用控制场景播放时 `defaults write dev.yif.StreamDock rhythmTraceSeconds -float 200`
  （写成文字也认），文件在 App 的临时目录 `streamdock-rhythm-trace.txt`。除三个频段外还记 5 个细分频段
  （30–150、150–400、400–2k、2–6k、6–16k Hz 的变化量，`FeatureExtractor.detailEdges`，只供离线研究），
  开头记下歌名和录制开始时播到第几秒，结果里的时间能换算成歌曲时间。
- **可比较分频**：`dock-probe bandcompare <trace>` 对比实时分析的分频（中频当军鼓）和建议的分频
  （2–6k 与 150–400 同时起音才算军鼓、6k 以上算镲片）识别出的底鼓、军鼓、镲片，按每 10 s 列出（歌曲时间）。
- **可对照**：录制时可在 M18 上按键打拍子，`dock-probe rhythm-eval` 计算与打拍的 F 值
  （±70 ms 容差，MIREX 惯例）。打拍只是**参考**：人打拍有延迟、不准，不作为标准答案，
  也不按它调参数；算法以信号本身的分析（录制数据、合成测试）为准。
- **可测试**：`RhythmKitTests` 用合成信号检验速度、拍点、状态切换。

## 打拍对照记录（仅供参考）

2026-10-24，用一首歌 200 s 的录制，听者在每个乐段按"感受最强的鼓点"打拍（166 下）：

| 作为"强拍"的事件 | F（±70 ms） | 精确率 | 召回率 |
|---|---|---|---|
| 网格拍（BPM + 相位） | 0.32 | 0.24 | 0.47 |
| 重击（本设计） | **0.62** | 0.51 | 0.78 |

结论：人感受到的强拍是"最突出的那几下打击"，不一定落在拍点网格上；网格只适合做底层律动。
重击参数在窗口 4–16 s、比例 25–35% 之间都在 0.60–0.62，是一个平台而不是尖峰，不是对这首歌过拟合。

已知问题：这首歌 150 s、170 s 附近速度跳到 173 / 77 BPM。网格现在只驱动柔和脉动，影响小；
后续可把 TempoEstimator 换成 HMM（速度为隐状态、相邻时刻速度连续）来根治。

### 开头频闪（2026-10-24）

现象：歌曲开头整条灯快速一亮一暗。录制开头 40 s 分析：重击每秒 2 次左右，每次都亮到 ≥50%，
间隙又几乎全黑（为了对比度）。根因是"有多重"完全用相对量衡量——重击挑选是 8 s 内排名，
大小也是排名，而底层 flux 本身又按 10 s 均值归一化、还是对数压缩的，安静段的打击看起来和
响亮段一样大。修正：引入线性幅度的 rawFlux，重击大小对比最近 60 s 的大击打（测试
`quietPassageAccentsAreSmallerThroughTheWholePipeline` 用真实合成音频验证）。

### 底鼓被当成轻拍（2026-10-24）

现象：有些段落底鼓不怎么亮。录制 60 s 分析：最响的 25% 低频打击（大底鼓）只有 38% 成为重击。
根因是"是不是重击"和"有多重"用了两把尺子：排名用对数、按均值归一化的 flux，它衡量的是
"多突然"而不是"多重"——低频一直有贝斯，底鼓显得不突然（≈8），军鼓在中频显得很突然（≈11），
于是排名选中军鼓；而按线性 rawFlux 算大小，军鼓只有底鼓的十分之一，结果是暗淡的重击占了
位置，还在半拍间隔内挡住了后面的底鼓。修正：排名和大小统一成一个量——各频段 rawFlux 对比
本频段自己的大击打。同一段录音大底鼓成为重击的比例 38% → 69%；剩下的都在底鼓很密的段落
（每 0.3 s 一下），8 s 内只取前 30% 是有意的。测试 `kicksAreAccentsNotLightBeats` 复现了
这个模式（旧算法失败、新算法通过）。打拍对照只作参考，不据此调参。

### 重击被吞、亮度无统一分配（2026-10-24）

旧渲染：亮度 = 0.32 + 0.22·响度·… + 0.8·脉冲，再截断到 1；新重击的目标若低于当前正在衰减的
脉冲就直接丢弃。同一段 60 s 录音里 30% 的重击看不出亮度变化。改为 GlowBudget：各层按比例、
滤色叠加，重击包络每次都升到 screen(当前, 大小)。重击可见（短灯条亮度上升 > 0.08）70% → 85%，
剩下的都在平缓段（按设计不闪）或强度刚起来时。测试：`ControlModulesTests/GlowLevelsTests`。

### 渲染的"土嗨感"（2026-10-24）

现象：重击亮灭太快、不柔和；流光时快时慢、频繁换向，灯珠高频闪烁。原因：重击是 40 ms 硬升 +
0.28 s 半衰；每个低/中频打击都给光团速度加一脚，还有概率直接反向；响度逐帧直接驱动亮度和宽度；
闪烁点一阶跟随、起步有拐角。修正见上方 ③：统一的临界阻尼包络、只加减速不换向的流光、平滑响度。
同一段 60 s 录音对比：每颗灯珠明暗换向 2.71 → 0.86 次/秒，单帧跳变 P99 0.144 → 0.071、
最大 0.56 → 0.23，重击可见率不变（82%）。测试 `flashIsSmooth` 检验包络形状。

### 光效品味（2026-10-24）

感知亮度 + 伽马输出 + 暗部防抖；OKLab 混色 + 峰值偏白；重击从一点扩散（重的铺满、轻的局部）；
封面配色在 OKLCh 里整理；暂停收成慢呼吸、停止才回场景色、切歌颜色渐变。同一段录音对比
（按感知亮度）：平滑度、亮度分布与上一版一致；局部亮起的重击 20 → 29 / 60。
测试：`GlowColorTests`、`PauseTests`。

### AirPlay / 组合播放采集（2026-10-24）

实测组合播放时，`com.apple.Music` 的音频进程输出设备为空，而
`com.apple.AirPlayXPCHelper` 在向本机显示器音频设备输出。只采集 Music 会得到静音。
采集现在每 2 秒检查 Music 的 AirPlay 状态及实际音频路由：Music 仍有输出时保留原来源；
仅当 Music 确认启用 AirPlay 且自身无输出时，改采集正在输出的 AirPlay 系统助手。
这是系统共享的 AirPlay 渲染进程，不能进一步按发送应用拆分；不使用全系统音频或麦克风作为回退。
进程、输出设备或默认输出变化时重建 tap；回调停止超过 5 秒也会重试。
聚合设备只包含 tap，避免混入物理设备的输入通道；无信号时维持配色流光。
纯远端播放没有本机可采集的输出时保留配色流光；没有本机输出的路由不因缺少回调反复重建。

实测验证：20:22:46 从 Music（进程对象 187）切换至 AirPlay 助手（176），
20:22:48 起持续收到 `signal=true`，节奏分析重新进入寻拍/锁定；本机播放与组合播放均已验证。

纯远端实测：取消本机播放后，Music 与 AirPlay 助手的输出设备列表均为空。
20:25 直接采集助手（176）仍没有音频回调与信号，因此现有 Core Audio tap 路径
不能为该模式提供真实律动；组合播放可用。没有自动更改用户的 AirPlay 设备选择。

### 活动亮度与 OBS 覆盖（2026-10-24）

音乐播放使用设置亮度，暂停慢呼吸使用设置亮度的一半。音乐输出未映射的浮点 LightPixel；此倍率与用户亮度由 LightEngine 合并，在最后的 LEDOutput 中仅做一次 Gamma 2.2 映射和暗部防抖。硬件总亮度固定 100%，不改变 GlowBudget 的感知亮度计算。OBS 录制/推流指示优先于音乐，通知优先于 OBS；覆盖期间音频分析继续，但只保留最近 0.25 秒的待消费节奏事件，避免积压与恢复时的旧事件突发。
